# nyan Real / Firmware Kit

電気メガネのファームウェアを **nyan Real / Spatial Wall** 向けに改修するためのツール。

*[English version](README.en.md)*

映像出力専用のメガネ型ディスプレイは、素の状態ではパネル本来の解像度を出さなかったり、
最上位の表示モードが隠されていたり、特定の入力機器で音が出なかったりします。
このリポジトリは、そうした制限を取り除いて Spatial Wall で快適に使えるようにするための、
機種ごとの手当てをまとめたものです。**必要なものは機種によって違います。**
ファームウェアの改修と書き込みが要る機種もあれば、既にハードウェアが持っている機能を
ホスト側から呼び出すだけで済む機種もあります。いずれも Spatial Wall を使わない場合でも
単体で有用です。

> **nyan Real / Spatial Wall** は電気メガネで空間ディスプレイを扱うためのアプリケーションです
> （Windows / macOS / GNOME / Raspberry Pi）。現在はマニュアルのみ先行公開で、本体は未公開です。
> → [nyan-real-spatial-wall](https://github.com/8796n/nyan-real-spatial-wall)

**本プロジェクトは XREAL（旧 Nreal）、Rokid をはじめとするいかなるメーカーとも関係がなく、
承認も後援も受けていません。** 各社の製品名・ブランド名は、このツールが対象とする
ハードウェアを特定する目的でのみ使用しています。メーカーのコード・ブランド・
ファームウェアはここでは一切配布しません。

## 最初に読んでください

**このツールはグラスのファームウェアを書き換えます。壊れる可能性があります。
そのリスクを全面的に引き受けられない場合は使わないでください。**

次の3点は同時に成り立っていて、3つとも理解する必要があります。

1. **ファームウェアは一切配布しません。ベンダーのものも、パッチ済みのものもです。**
   パッチ済みイメージは 99% 以上がベンダーのコードです。公式ファームウェアはあなた自身が
   用意し、このリポジトリはそれをあなたの手元でパッチ済みイメージに変換します。

2. **入手した公式ファームウェアのファイルは、あなたの復旧手段です。**
   保管してください。1年後にも手元にある場所へバックアップしてください。それを失った状態で
   書き込みに失敗した場合、このリポジトリにできることはありません。

3. **本体から吸い出せるかは機種によります。当てにしないでください。**
   XREAL Air（第1世代）については、純正 MCU アプリケーションの静的解析で
   **読み出し不可を確認済み**です。ホストがアドレスと長さを指定してアプリ領域や
   ブート領域を読み出せる message id は存在せず、ツール側でバックアップを取ることは
   原理的にできません。他機種の状況は各機種のセクションに書きます。

**メーカー公式のアプリは動かなくなる可能性があります。** 詳細は
[純正アプリについて](#純正アプリについて)を参照してください。

ベンダーのファームウェアの提供・ホスティング・ミラー・入手方法の説明は行いません。
入手方法を尋ねる質問にも回答しません。ファームウェアのバイナリやダウンロードリンクを含む
Issue および Pull Request は削除します。

## 対応機種

| 機種 | 状態 |
|---|---|
| XREAL Air（第1世代） | **対応済み。** DP ブリッジと MCU の両方 |
| XREAL Air 2 | 予定。720p 対応を中心に |
| Rokid Max | 予定。ファームウェア改修ではなくホスト側の表示モード制御になる見込み（下記） |
| xbx a01 系 | 予定 |

機種ごとの内容と検証記録は各機種のディレクトリにあります。以下は現在対応済みの
XREAL Air（第1世代）についての説明です。

### Rokid Max について（予定）

Rokid Max は事情が違います。**EDID は MCU ファームウェアではなく DP ブリッジ
（LT7911UX）側にあり**、そのファームウェアは公開も吸い出しもできません。したがって
XREAL Air でやったような EDID の書き換えはできません。

そのかわり、**最上位の表示モードはハードウェアに最初から存在します。**
`3840x1200@90`（片眼 `1920x1200@90`）は USB 制御転送で選択できますが、公式 SDK は
下位2モードしか公開しておらず、本体ボタンからも到達できません。ここに手を入れる価値があります。

MCU（STM32）側は DFU で吸い出しも書き込みもできるため、必要になれば改修も可能です。
ただし最新版の公式ファームウェアの入手には Rokid Station 2 が必要で、アプリに同梱されている
のは古い版です。

## 必要なもの — XREAL Air（第1世代）

| 対象 | ファイル | SHA-256 |
|---|---|---|
| DP ブリッジ | `1140` | `66A28C7BE1842D6837C68A5586CB0465099787F421427BE0CBE9691C858837DA` |
| MCU | `07.1.02.387_20240428.bin` | `B1784C6D618D3CF6F03D77A93442C3267A425CB2BE415E8912539E165645A3E7` |

Air（第1世代）の公式イメージです。ハッシュを公開しているのは、入手したファイルが
このツールの想定するものと同一かを検証するためです。ビルダは一致しないファイルを拒否します。

入手したファイルは `firmware/` に置いてください。このディレクトリは gitignore されており、
中身がコミットされることはありません。

### Python まわり

Python 3.10 以降。**必要なライブラリは使うツールによって違います。**

| 用途 | 必要なもの |
|---|---|
| イメージをビルドする | **なし。** 標準ライブラリだけで動きます |
| EDID を読む / Windows の表示信号を見る | **なし。** OS が持っている情報を読むだけです |
| グラスへ書き込む / レジスタを読む | `hidapi` |

```bash
pip install -r requirements.txt
```

PyPI には `import hid` を提供するパッケージが2つあります。**必要なのは `hidapi`** の方で、
コンパイル済みのバインディングが同梱されています。もう一方の `hid` は別途システムに
libhidapi が要る ctypes ラッパーです。両方入れると import が混乱します。

### 対応 OS

**検証したのは Windows です。**

| ツール | Windows | Linux / macOS |
|---|---|---|
| `xreal/air/build_dp.py` / `build_mcu.py` | 動く | **動く**（純粋な Python） |
| `xreal/dp_flash.py` / `mcu_flash.py` | 動く | 動くはず（未検証） |
| `xreal/display.py` / `dpreg.py` / `panelreg.py` / `vsync.py` | 動く | 動くはず（未検証） |
| `xreal/edid_dump.py` | 動く | **動きません**（PowerShell と WMI を使います） |
| `common/display_signal.py` | 動く | **動きません**（Windows の表示設定 API を使います） |

イメージのビルドはどの OS でもできます。グラスと話すツールは hidapi しか使っていないので
Linux や macOS でも動くはずですが、**こちらでは確認していません。**

`xreal/display.py --probe` は切替後に `edid_dump.py` を呼ぶため、この組み合わせだけは
Windows が要ります。モードの読み書きだけなら OS を問いません。

**Linux では HID デバイスへのアクセス権が要ります。** root で実行するか、udev ルールを
置いてください。

```
# /etc/udev/rules.d/70-xreal.rules
SUBSYSTEM=="hidraw", ATTRS{idVendor}=="3318", MODE="0666"
```

## 何をするツールか — XREAL Air（第1世代）

純正ファームウェアは 1080p しか広告しません。パネルは 1920x1200 なのにその解像度は
提示されず、720p しか出せない機器には対応するタイミングが無く、USB を持たない機器では
音が出ません。このキットは4つの入力経路すべてを扱えるようにします。

| 入力 | 純正 | このビルド |
|---|---|---|
| `1280x720` | 対応タイミングなし | **CTA に VIC 4 を広告。** ブリッジが全画面へ拡大 |
| `1920x1080` | ネイティブ | 変更なし。60 / 90 / 120 Hz |
| `1920x1200` | 提示されない | **preferred timing。** 60 / 90 / 120 Hz |
| `3840x1200` Full-SBS | `3840x1080` | **3840x1200 @ 60 / 72 / 90 Hz**（HBR2） |

論理モード別の広告内容は次のとおりです。

| 論理モード | 純正 | このビルド |
|---:|---|---|
| 1（自動） | `1080p60/90/120` | **`1200p60` が preferred**、`1200p90`、`1200p120`。CTA に `1080p60/90/120` と `720p60` |
| 5 / 10 / 11（固定リフレッシュ） | `1080p` のみ | **`1200p72/90/120` が preferred**、同リフレッシュの `1080p` を副として広告。CTA は漏れない |
| 3 / 4 / 9（Full-SBS 3D） | `3840x1080` | **`3840x1200` @ 60 / 72 / 90 Hz**（HBR2） |

すべての 2D モードが EDID の preferred timing として 1920x1200 を広告します。preferred timing から
「ネイティブ解像度」を決めるホスト、とくに macOS が、1200p をまったく選ばない状態から
既定で選ぶ状態に変わります。

パネルの行数、パネルのタイミンググループ、DP のリンクレート、入力分類はすべて実際の入力信号に
自動追従します。ホスト側で解像度やリフレッシュを切り替えても、グラス側の操作は要りません。

### DP 音声の自動切替

**HDMI → USB-C 変換器やゲーム機は USB データを一切運びません。** USB オーディオが使えず、
かといって手動切替のボタンを押す人もいない状況になります。純正ファームウェアでこの状態から
音を出すには、利用者が長押しで切り替えるか、純正 Nreal Adapter が専用のビットを立てるかの
どちらかが必要です。

このビルドの MCU は USB の `SET_ADDRESS` を監視します。

- ホストが一度でもデバイスをアドレス指定すれば、その給電セッションでは **USB オーディオのまま**
  保持します。PC 直結が誤って DP 音声に落ちることはありません
- アドレスが 0 のまま約5秒続いた場合にだけ、純正の DP 音声遷移へ入ります
- 純正 Nreal Adapter の Attention 経路は純正と同じく即時に動作します
- 切替時に保存済みの音量を復元し、その給電セッション中は手動切替をロックします

なお **DP 音声モードに入ると USB 複合デバイスが閉じます。これは純正の挙動です。**
そのため DP 音声中は HID 制御が使えません。

**ホスト側の既知の注意点。** NVIDIA のドライバは、ディスプレイのネイティブ解像度より小さい
モードを GPU でスケーリングします。ネイティブが 1200p になったことで、1080p を選ぶと
真の 1080p 信号ではなく引き伸ばしになる場合があります。NVIDIA コントロールパネルで
スケーリングを「なし」にすると解消しますが、この設定は EDID 構成ごとに保存されるため、
使いたい論理モードごとに一度ずつ設定する必要があります。1200p で常用する場合は関係ありません。

XREAL の純正コンテナは複数機種の EDID テンプレートを内包しており、ヘッダの project code が
どれを使うかを決めます。Air（第1世代）のビルダは Air 用テンプレートだけを変更し、
他機種のブロックは純正とバイト単位で同一のまま残します。

## 純正アプリについて

**メーカー公式のアプリはこのキットの検証対象外です。** 動かなくなる、あるいは想定外の
挙動になる可能性があります。改造ファームウェアを入れる前に、そのアプリに依存しているか
考えてください。

### 版数は変えていません

このビルドはヘッダに一切触れないので、**グラスが報告するファームウェア版数は純正のまま**です
（DP は `1140`、MCU は `07.1.02.387_20240428`）。これは両面あります。

- アプリは版数の食い違いで更新を促してきません
- しかし**アプリがファームウェア更新を実行すれば、改造は純正で上書きされます**

上書きされても壊れるわけではありません。このキットで焼き直せば戻ります。ただし
**気づかないうちに元に戻っていることがある**ので、挙動がおかしくなったら
`python xreal/edid_dump.py` で今どちらが入っているか確認してください。

### 仕組み上ぶつかるところ

- **DP 音声中はアプリがグラスと通信できません。** USB 複合デバイスが閉じるためで、
  これは純正の挙動です。ただしこのビルドは USB データを持たない機器で**自動的に**
  DP 音声へ移るので、純正より遭遇しやすくなります
- **自動切替の後、その給電セッション中は手動の音声切替がロックされます。**
  アプリからの音声切替も効きません。抜き差しで解除されます
- **EDID が純正と違うモードを広告します。** 1080p 固定を前提にしているアプリは
  想定外の解像度を見ることになります

### 元に戻したい場合

入手した純正ファイルを書き戻してください。

```bash
python xreal/dp_flash.py  --restore --flash
python xreal/mcu_flash.py --restore --flash
```

`firmware/` に純正ファイルが置いてある必要があります。

## 使い方

DP ブリッジと MCU は**必ず対で扱ってください。** 片方だけを入れ替えると、パネルが入力に
追従しない、音声が切り替わらない、といった不整合が起きます。

自分で用意した純正ファイルから2つのイメージを作ります。

```bash
python xreal/air/build_dp.py  --src firmware/1140                     --out air-dp.bin
python xreal/air/build_mcu.py --src firmware/07.1.02.387_20240428.bin --out air-mcu.bin
```

ビルダは処理の各段階で検証を行い、どこかで食い違えば必ず失敗します。`--force` はありません。
書き出さずに検証だけ行うこともできます。

```bash
python xreal/air/build_dp.py --src firmware/1140 --check-only
```

ビルダが出力するイメージの SHA-256 は固定です。手元の結果がこれと一致すれば、
このリポジトリで検証したものとバイト単位で同一です。

| イメージ | SHA-256 |
|---|---|
| DP | `D5D34FB0ED0AB49B92D793CCF8384E61B1C1274AAC45293911F3CAF325BDC793` |
| MCU | `3842A4232356B993CFDE839B3D772EB861FC382B0506EF2098E1352F100A77FE` |

そのうえで書き込みます。**ここが不可逆な部分です。**

```bash
python xreal/dp_flash.py  --image air-dp.bin  --flash
python xreal/mcu_flash.py --image air-mcu.bin --flash
```

DP は FINISH 後に自分で再起動するので抜き差しは不要です。MCU は bootloader を経由して
アプリケーションへ復帰します。

`xreal/dp_flash.py` を引数なしで実行するのは安全です。接続中のグラスを識別し、動作中の
ファームウェアのバージョンを表示するだけで、何も書き込みません。まずこれを実行してください。

## なぜこのビルドを信用できるか

ビルダは単にパッチを当てるだけでなく、結果を証明します。

- 純正イメージの SHA-256、project code、コンテナ CRC が想定と一致すること
- 変更内容は before / after を逐語で持つラベル付きレコードの表であること。2つのイメージを
  自分で diff すれば表そのものを監査できます
- 各レコードの before バイトが適用前に一致すること
- ビルドが決定論的であり、出力の SHA-256・コンテナ CRC・bank0 commit tag・変更バイト数が
  すべて pin されていること
- 生成された EDID をデコードし、論理モードごとの広告内容が契約どおりであること
- ファームウェア自身の 8051 post-build helper を小さなエミュレータで実行し、どのモードが
  どの EDID timing スロットに何を書くかを全状態ベクタで実証すること

各リリースの設計判断と実機での検証記録は `xreal/air/docs/` にあります。

## うまくいかなかったとき

実際に観測された故障モードと、その復旧方法です。

**project code の不一致。** コンテナヘッダの project code が機種を選択します。別機種向けに
ビルドされたイメージを書き込むとグラスが壊れる可能性があります。ビルダもフラッシュツールも
不一致を拒否します。この判定を無効化しないでください。

**DP ブリッジが fallback イメージで起動する。** bank0 commit tag が一致しないと、ブリッジは
bank0 を拒否して内部の fallback イメージに落ちます。症状はバージョン `1109`、モニタ名
`nreal air`、60 Hz 固定、モード切替不能。**これは復旧可能です。** 同じツールで正常な
イメージを焼き直してください。

**MCU が起動しない。** 不正な MCU イメージはアプリケーションを起動不能にすることがあり、
USB の接続と切断を繰り返す状態になります。ボタンを保持したまま USB を接続すると
bootloader（PID `0x0423`）に入るので、純正 MCU イメージを全書き戻ししてください。
実際にこの手順で完全に復旧した実績があります。

**転送が中断した、FINISH が異常ステータスを返した。** 再試行の前に抜き差しでリセットして
ください。正常に書き込めた場合は抜き差し不要です。ブリッジは自分で再起動します。

## 構成

```
xreal/          XREAL 共通。HID プロトコル、書き込み、診断ツール
  air/          Air（第1世代）のビルダと設計・検証ドキュメント
common/         ベンダー非依存のツール
docs/           コンテナ形式、プロトコル、共通の背景知識
firmware/       あなたが用意した純正ファイルの置き場所（gitignore）
```

**`xreal/` 直下のツールが対象にしているのは Air 系です。** Air（第1世代）で検証済みで、
Air 2 / Air 2 Pro も同じ USB HID プロトコル（VID `0x3318`）を使います。

**同じ VID を持っていても、別系統の機種では動きません。**

| 機種 | `xreal/` のツール |
|---|---|
| Air（第1世代） | 検証済み |
| Air 2 / Air 2 Pro | 同じプロトコル。このキットでは未検証 |
| XREAL One / One Pro / 1S | **動きません。** 16bit op の別プロトコルです |
| xbx a01+（x by XREAL） | 同じプロトコル系統。細部に差異あり。未検証 |

Rokid はさらに違い、USB 制御転送と DFU で共通点がありません。
今後 `rokid/` などがベンダー単位で並びます。

`common/` に入るのはデバイスの知識を持たないものだけです。現状は Windows が
デスクトップ解像度と線上信号のどちらを出しているかを表示するツールが1本あります。

書き込みツールはコンテナヘッダの機種識別子を照合するので、別機種向けのイメージを
取り違えて焼くことはできません。

### 診断ツール

いずれもファームウェアには書き込みません。ただし**必要な前提が違います。**

| ツール | 純正ファームで動くか | 内容 |
|---|---|---|
| `common/display_signal.py` | 動く（機種非依存） | デスクトップ解像度と線上信号を分けて表示 |
| `xreal/edid_dump.py` | 動く | ホストが受け取った EDID をデコード、スナップショット比較 |
| `xreal/display.py` | 動く | 論理表示モードの取得と切替 |
| `xreal/vsync.py` | 動く | パネル VSYNC の実測 |
| `xreal/dpreg.py` | **動かない** | DP ブリッジのレジスタ読み出し |
| `xreal/panelreg.py` | **動かない** | パネルレジスタの読み書き |

`dpreg.py` と `panelreg.py` は**本キットの MCU ビルドが追加するレジスタ peek** を使います。
純正ファームウェアにはこの機能が無いため、前者はタイムアウトし、後者は全レジスタが `0x23` を
返します。どちらもその状態を検出して明示するので、誤った値を報告することはありません。

完全に受動的でないものが2つあります。`display.py` は切替時に HPD をトグルするので画面が
数秒落ちます（モード自体は揮発で、抜き差しすれば既定に戻ります）。`panelreg.py` は書き込みも
できますが、パネルレジスタは RAM 上にあるため電源を入れ直せば元に戻ります。
