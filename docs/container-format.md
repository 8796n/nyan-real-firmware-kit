# ファームウェアコンテナの形式 — Air 系 / xbx a01 系

DP ブリッジ用イメージと MCU 用イメージは、同じ発想の小さなコンテナに包まれています。
ヘッダに CRC とサイズと素性が入り、その後ろにペイロードが続くだけです。

この文書は、`xreal/air/build_dp.py` と `xreal/air/build_mcu.py` が何を検証しているのか、
`xreal/dp_flash.py` が書き込み前に何を拒否するのかを読めるようにするためのものです。

**コンテナは1種類ではありません。** 実物を見た範囲では2つの形があります。

| 形式 | ヘッダ | CRC 格納 | 使っているイメージ |
|---|---|---|---|
| **A（標準形）** | `0x40` バイト。projectCode と fwType を持つ | LE | Air / Air 2 / xbx a01+ の DP イメージ（fwType 2）、Air 2 / xbx a01+ の MCU イメージ（fwType 1） |
| **B** | 24 バイト。projectCode も fwType も無い | BE | **Air（第1世代）の MCU イメージ** |

**Air（第1世代）の MCU だけが形式 B です。** 実物を見た範囲では、これが唯一の例外です。
同じ「MCU のファームウェア」でも Air 2 と xbx a01+ は形式 A を使います。
機種と役割の組み合わせごとに確かめてください。

**そして、コンテナが同じでも中身は別物です。** xbx a01+ の DP イメージは形式 A の
コンテナに包まれていますが、ペイロードの EDID の持ち方は Air 系とまったく違います
（後述）。コンテナが読めることと、中の構造が同じであることは別の話です。

**XREAL One / One Pro / 1S は別アーキテクチャで、どちらの形式を使っているという根拠も
ありません。** 後述の projectCode 表に載っているのは、Air 系ファームウェアが内部に持っている
機種対応表だからであって、それらの機種のファームウェアがこのコンテナに包まれている
という意味ではありません。

---

## DP ブリッジのコンテナ

先頭 `0x40` バイトがヘッダで、`0x40` 以降がペイロードです。**サイズはイメージごとに違います**
（Air / Air 2 の `1140` は `50,632` バイト、xbx a01+ の `001C` は `59,866` バイト）。
ヘッダの構造は共通です。

| オフセット | サイズ | 内容 |
|---|---:|---|
| `0x00` | 4 | コンテナ CRC-32（**リトルエンディアン格納**） |
| `0x04` | 4 | length（リトルエンディアン）。CRC の対象範囲を決める |
| `0x08` | 4 | projectCode。どの機種向けのイメージか |
| `0x0C` | 4 | fwType。DP ブリッジは `2` |
| `0x10` | 20 | 名前。NUL 終端。DP は `"1140"` |
| `0x24` | 14 | ビルド文字列 |
| `0x38` | 1 | **bank0 commit tag** |
| `0x40` | — | ペイロード |

**コード番地とファイルオフセットの対応は `code = file - 0x40`** です。ペイロードは 8051 の
コードで、ドキュメントやコード内で「code 0x1148」と書かれていればファイル `0x1188` を指します。

### コンテナ CRC-32

```
poly      0xF4ACFB13
init      0
入力反転  なし
出力反転  なし
xorout    0
対象範囲  d[8 : 8+length]
格納      d[0:4] にリトルエンディアン
```

一般的な CRC-32 とは多項式も反射も違います。標準ライブラリの `zlib.crc32` では合いません。

### bank0 commit tag

**ここが一番重要です。** DP7911 のブートはこのタグを検証し、合わなければ bank0 を拒否します。

```
poly      0x31 (CRC-8)
init      0
MSB first / 反転なし / xorout 0
対象範囲  ペイロード(file 0x40..EOF) を 0xFF で 0xFFFF バイトまでパディングしたもの
格納      d[0x38]
```

ブート側の判定は「タグを含めた bank0 全体の CRC-8 が 0 になるか」です。つまり
パディング済みペイロードの末尾にタグ 1 バイトを足して CRC-8 を取り、0 なら合格。

**タグが合わないと何が起きるか。** ブリッジは bank0 を捨て、bank0 の外にある fallback
イメージで起動します。症状は次のとおりです。

- ファームウェア版数が `1109` になる（正常なら `1140`）
- モニタ名が `nreal air` になる
- 60 Hz 固定になり、表示モードの切替が効かなくなる

**この状態からは復旧できます。** 正しいイメージを同じツールで焼き直せば戻ります。
ブートローダごと壊れているわけではありません。

### projectCode

**ヘッダの projectCode だけが機種を決めます。ファイル名も名前フィールドも判別材料になりません。**
`1140` という名前のイメージは Air（projectCode `0x0700`）にも Air 2 / Air 2 Pro（`0x0900`）にも
存在し、ペイロードもほぼ共通で、違うのは projectCode です。

| projectCode | 機種 |
|---|---|
| `0x0700` | Air（第1世代） |
| `0x0900` | Air 2 / Air 2 Pro |
| `0x1200` | Air 2 Ultra |
| `0x1500` | XREAL One / One Pro |
| `0x1900` | xbx a01+ |

**この表は Air 系ファームウェアが内部に持っている対応表です。** このキットの対応機種一覧でも、
「これらの機種が同じコンテナ形式を使う」という主張でもありません。ビルダで検証済みなのは
Air（第1世代）だけです。

**別機種の projectCode を持つイメージを焼くとグラスが壊れる可能性があります。**
ビルダは想定外の projectCode を拒否し、フラッシュツールは接続中の PID から求めた
projectCode とイメージのそれを突き合わせて、違えば書き込みを中止します。

### EDID の持ち方はペイロードごとに違う

**ここから先はコンテナの話ではなく、Air / Air 2 系ペイロードの中身の話です。**
同じコンテナに包まれていても、ペイロードが EDID をどう持つかは共通ではありません。
たとえば xbx a01+ の `001C` には、以下に書く多機種テーブルも実行時 DTD 合成も
**どちらも存在しません**（EDID バッファは 512 バイトで、拡張ブロックは素通しされます）。

#### 複数機種の EDID テンプレートが同居している（Air / Air 2 系）

ペイロードには機種ごとの静的 EDID ブロックが 128 バイトずつ並んでいます。

| ファイルオフセット | 機種 | モニタ名 |
|---|---|---|
| `0x1D5C` | Air（第1世代） | `Air` |
| `0x1DDC` | HONOR Glass | `HONOR Glass` |
| `0x1E5C` | Air 2 | `Air 2` |
| `0x1EDC` | Air 2 Pro | `Air 2 Pro` |
| `0x1F5C` | Air 2 Ultra | `Air 2 Ultra` |

どれを使うかは実行時に機種 ID で選択されます。**このキットの Air 用ビルダは
`0x1D5C` のブロックだけを変更し、他機種のブロックは純正とバイト単位で同一のまま残します。**

#### 静的テンプレートと実行時ビルダ（Air / Air 2 系）

ホストが受け取る EDID は、この静的ブロックそのままではありません。ファームウェアは
実行時に詳細タイミング（DTD）を組み立ててブロックへ書き込み、その後でチェックサムを
計算し直します。

見分け方があります。DTD のバイト 12-14 は本来「画面の物理サイズ mm」ですが、
実行時ビルダはそこに **Hactive / Vactive をそのまま入れます**。
`xreal/edid_dump.py` はこれを判定して表示します。

XDATA 上のレイアウトは次のとおりです。

```
0x022B   base EDID ブロックの先頭
 +54     DTD スロット 0   (0x0261)
 +72     DTD スロット 1   (0x0273)
 +90     DTD スロット 2   (0x0285)
 +108    DTD スロット 3   (0x0297)
 +126    拡張ブロック数
 +128    CTA 拡張ブロック (0x02AB)
```

スロット 3 にはモニタ名記述子が入り、スロット 2 は使われ方がモードによって変わります。

この XDATA 配置と DTD 合成は Air（第1世代）で確認したものです。**別のペイロードに
同じ配置を期待しないでください。**

## MCU のコンテナ

**機種によって形式が違います。**

### Air（第1世代）— 形式 B

サイズは `153,888` バイト固定。ヘッダは 24 バイトで、DP とは**エンディアンが違います。**

| オフセット | サイズ | 内容 |
|---|---:|---|
| `0x00` | 4 | コンテナ CRC-32（**ビッグエンディアン格納**） |
| `0x04` | 4 | length（リトルエンディアン）。`0x25918` = ファイルサイズ - 8 |
| `0x08` | 16 | 名前。`"Air.BootV_0.0.1"` |
| `0x18` | — | ペイロード |

**projectCode も fwType もありません。** 機種の判別材料はこの名前だけです。
`xreal/air/build_mcu.py` は名前が `"Air."` で始まることを確認します。

CRC の多項式と対象範囲は DP と同じ（`poly 0xF4ACFB13`、`d[8 : 8+length]`）で、
**格納だけがビッグエンディアン**です。bank0 commit tag は DP ブリッジのブートの仕組みなので、
MCU のコンテナにはありません。

### Air 2 — 形式 A

サイズは `151,160` バイト。**ヘッダは DP イメージと同じ標準形**で、CRC も LE 格納です。

| オフセット | 内容 |
|---|---|
| `0x00` | コンテナ CRC-32（リトルエンディアン格納） |
| `0x04` | length。`0x24E70` |
| `0x08` | projectCode `0x0900`（Air 2 / Air 2 Pro） |
| `0x0C` | **fwType `1`**（DP イメージは `2`） |
| `0x10` | 名前。`"09.1.00.180_2024..."` |

**fwType が DP と MCU を分けます。** projectCode を持つので、機種の突き合わせも DP と
同じやり方でできます。

同じ「MCU のファームウェア」でも Air と Air 2 でここまで違うので、**新しい機種に触るときは
まずヘッダを 32 バイト読んで、どちらの形式か確かめてください。**

ペイロードは ARM Thumb コードで、先頭がベクタテーブルです。

```
VA          = file offset + 0xEFE8
file offset = VA - 0xEFE8
```

この対応はベクタテーブルから確認できます。`file 0x18` の先頭 2 ワードが初期スタックポインタ
`0x2001C9E8` とリセットベクタ `0x0000F259` で、Thumb ビットを除いた `0xF258` が
`file 0x270` に対応し、そこが実際にコードとして成立しています。

`xreal/air/build_mcu.py` はコンテナ CRC のほかに、初期スタックポインタが SRAM の範囲に
あること、リセットベクタがペイロード内を指していることも確認します。

## 検証の順番

ビルダもフラッシュツールも、同じ順で確かめてから先へ進みます。

1. **サイズ** — その機種・その役割の固定長と一致するか
2. **素性** — 形式 A なら projectCode と fwType、形式 B なら名前
3. **コンテナ CRC** — ヘッダの値と再計算が一致するか（**格納のエンディアンに注意**）
4. **bank0 tag**（DP のみ）— ブートが受け入れる値か
5. **SHA-256** — 既知のイメージと完全一致するか

このうち 1〜4 は**イメージ単体で判定できる**ので、素性の分からないファイルに対しても
そのまま使えます。5 はこのキットが検証済みのイメージかどうかを見るものです。

フラッシュツールはさらに、**接続中のグラスの projectCode とイメージのそれが一致するか**を
確認します。ここが不一致なら書き込みません。
