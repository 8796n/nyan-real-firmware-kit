# XREAL Air 系の USB HID プロトコル

*[English version](hid-protocol.en.md)*

`xreal/` 以下のツールがグラスと話すための仕様です。読み出し系のコマンドも書き込み系も、
同じ 64 バイトのフレームに乗ります。

実装は `xreal/glasses.py`（フレーム組立・解析とデバイス判別）にまとまっています。

**適用範囲。** 64 バイトのフレーム形式、DP 書き込みの手順（110-113）、MCU 書き込みの
msgid（62 / 68 / 38）は、**Air（第1世代）と xbx a01+ の両方で確認**しています。
Air 2 / Air 2 Pro も同じ形式です。

**XREAL One / One Pro / 1S はここに書いた方式ではありません** —— 16bit の op を使う
別プロトコルで、`xreal/` のツールは動きません。

同じ形式でも**機種ごとに実装されている msgid は違います**（後述）。

---

## デバイスの識別

VID は XREAL 製品で共通の `0x3318` です。PID が機種と状態を表します。

| PID | 機種 | 状態 | このキットでの扱い |
|---|---|---|---|
| `0x0424` / `0x0423` | Air（第1世代） | APP / BOOT | 検証済み |
| `0x0428` / `0x0427` | Air 2 | APP / BOOT | 同じプロトコル。未検証 |
| `0x0432` / `0x0431` | Air 2 Pro | APP / BOOT | 同じプロトコル。未検証 |
| `0x0441` / `0x0442` | xbx a01+ | APP / BOOT | 同じ系統。未検証 |

`xreal/glasses.py` の PID 表は**接続されているものを識別するため**のもので、
対応機種の一覧ではありません。One 系（`0x0436` / `0x043E` など）は表に載せていません。

**APP と BOOT は MCU の状態であって、DP ブリッジの状態ではありません。**
BOOT で見えているのは「MCU がブートローダにいる」というだけで、DP ブリッジは無関係に動きます。

インタフェース番号は次のとおりです。

| 番号 | 用途 |
|---:|---|
| 3 | IMU |
| **4** | **制御（MI_04）。ほぼ全てのツールがここを開く** |
| 5 | パネル VSYNC の通知（エンドポイント `0x88`） |

**ブートローダは例外で、インタフェースを1本（IF0）しか出しません。**
`CTRL_IF` を決め打ちすると BOOT を永久に見逃します。`xreal/mcu_flash.py` は
その PID で実際に列挙されたインタフェースから選びます。

**DP 音声モードに入ると USB 複合デバイスが閉じます。これは純正の挙動です。**
そのため DP 音声中は HID がまったく列挙されず、どのツールも使えません。

## フレーム形式

report id 0 の 64 バイトレポートです。足りない分は 0 で埋めます。

```
[0]      0xFD              マジック
[1:5]    CRC32-LE          [5 : 5+len) が対象
[5:7]    len-LE            = 17 + payload 長
[7:11]   seq
[11:15]  timestamp
[15:17]  msgId-LE
[17:22]  パディング 5 バイト
[22:]    payload           最大 42 バイト
```

**CRC は標準の CRC-32（zlib と同じ）** です。コンテナの CRC とは別物なので混同しないでください。

応答も同じ形で返り、`[22]` が status、その後ろがデータです。

```
msgId  = [15] | [16] << 8
status = [22]
data   = [23:]
```

**ack の判定は経路で違います。**

| 経路 | ack とみなす status |
|---|---|
| DP ブリッジ書き込み | `0` または `250`（`0xFA`） |
| MCU 書き込み | `0` のみ |

`[17:22]` の 5 バイトはパディングで、ハンドラはここを読み飛ばして `[22]` から見ます。

payload を空にしてフレームを組んではいけません。16 バイトのフレーム（len `0x000B`）は
xbx a01+ の MCU をクラッシュさせます。Air で同じことが起きるかは確かめていません。

`xreal/glasses.py` の `build_fd()` は msgid を 1 バイトとして扱うので、呼び出し側は
**6 バイト**のパディングを渡します。その 1 バイト目が msgid の上位バイト（常に 0）になり、
残る 5 バイトが上記のパディングに収まります。結果は同じバイト列です。

**同じフレーム形式でも機種ごとに差はあります。** たとえば msgid 237（レジスタ読み出し）は
a01+ には実装されていますが Air にはありません。フレームが通ることと、任意の msgid が
実装されていることは別です。

## DP ブリッジの書き込み

| msgid | 名前 | payload |
|---:|---|---|
| 110 (`0x6E`) | PREPARE | 空 |
| 111 (`0x6F`) | START | 先頭 64 バイトを 2 フレームに分割 |
| 112 (`0x70`) | TRANSMIT | 残りを 42 バイトずつ |
| 113 (`0x71`) | FINISH | 空 |

手順は次のとおりです。

```
PREPARE(110)
START(111)     fw[0:42]
START(111)     fw[42:64]      ← コンテナヘッダを 2 本に割る
TRANSMIT(112)  fw[64:] を 42 バイトずつ  (50,632 バイトなら 1,204 回)
FINISH(113)    MCU がコンテナ CRC を照合。不一致なら status 5
```

**FINISH が ack されれば、ブリッジは自分で再起動して新しいイメージで動き始めます。**
抜き差しは要りません。

失敗したときだけ話が変わります。FINISH が非正常 status を返した、タイムアウトした、
転送が途中で切れた —— この場合 PREPARE はヘッダカウントと SPI の書き込みオフセットを
戻さないため、**同じ電源セッション内での再試行は危険です。** 一度抜き差ししてから再試行してください。

成功した書き込みを繰り返すのは安全です。抜き差しを挟まずに 9 回連続で書き込み、
毎回 FINISH ack と版数 `1140` を確認しています。

## MCU の書き込み

MCU はブートローダへ落ちてから書きます。**アプリ領域しか書き換わらないので、
アプリを壊してもブートローダから復旧できます。**

| msgid | 名前 | payload |
|---:|---|---|
| 62 | PREPARE | 空 |
| 68 | JUMP_TO_BOOT | 空 |
| 63 | START | `fw[0:24]` = コンテナヘッダちょうど |
| 64 | TRANSMIT | `fw[24:]` を 42 バイトずつ |
| 65 | FINISH | 空 |
| 66 | JUMP_TO_APP | 空 |

```
PREPARE(62)
JUMP_TO_BOOT(68)      ← 応答を待たない
[BOOT PID で再列挙]
START(63)             fw[0:24]
TRANSMIT(64)          fw[24:] を 42 バイトずつ
FINISH(65)            ブートローダがコンテナ CRC を照合
JUMP_TO_APP(66)
```

`JUMP_TO_BOOT` は**送りっぱなしにします。** 応答を待つと OSError で落ちるうえ、待っている間に
ブートローダの受付窓を逃します。更新が続かないとブートローダはアプリへ戻ってしまうためです。

実測したタイミングは次のとおりです。

- `JUMP_TO_BOOT` の約 0.35 秒後にデバイスが消える
- 約 1.37 秒で BOOT PID が現れる
- **BOOT に留まるのは約 15 秒。** 転送を始めれば延びますが、`START` までは寄り道しないこと

**既に BOOT にいるなら `PREPARE` と `JUMP_TO_BOOT` は要りません。** アプリを壊して
BOOT で立ち往生したときの復旧路がこれです。`xreal/mcu_flash.py` は BOOT を検出したら
そのまま転送に入ります。

## 読み出し系

| msgid | 内容 |
|---:|---|
| 22 | DP ブリッジのファームウェア版数 |
| 38 | MCU アプリのファームウェア版数 |
| `0x07` | 現在の表示モード |
| `0x08` | 表示モードの設定 |

`0x07` は**書いた値の読み戻しではなく、DP リンクの現在の状態**を返します。ホスト側で
リフレッシュレートを変えても値が動くので、`0x08` で書いた値と一致したからといって
切替が効いた証明にはなりません。

表示モードは揮発です。抜き差しすれば既定へ戻ります。切替の際に HPD がトグルするため、
画面が数秒落ちます。これが EDID の再読み込みを起こすトリガでもあります。

### このキットが追加する peek

純正ファームウェアには、ホストが番地を指定してレジスタを読む手段がありません。
このキットの MCU ビルドは 2 つ追加します。

| msgid | 対象 | 要求 | 応答 |
|---:|---|---|---|
| `0x29` | DP ブリッジのレジスタ | `[0xA5, page, reg]` | 値 1 バイト |
| `0x5B` | パネルのレジスタ | `[0xA5, eye, reg]` 読み / `[0x5A, eye, reg, val]` 書き | 値 1 バイト |

**純正ファームウェアに対しては、前者はタイムアウトし、後者は全レジスタが `0x23` を返します。**
`xreal/dpreg.py` と `xreal/panelreg.py` はこれを検出して明示するので、
誤った値を報告することはありません。

パネルレジスタは RAM 上にあるので、書き間違えても電源を入れ直せば戻ります。
ただし `reg 0x82` はバンク選択なので、読み書きが終わったら 0 に戻してください。

## 移植するときに見る順番

別機種へ広げる場合、確認する順番はこうなります。

1. **VID / PID とインタフェース構成** — 制御インタフェースがどれか。ブートローダは何本出すか
2. **フレーム形式が同じか** — マジック `0xFD`、CRC の位置と種類、len の数え方
3. **msgid が同じか** — 版数読み出しで往復できれば、フレームは合っている
4. **コンテナ形式** — [container-format.md](container-format.md) を参照
5. **書き込み手順** — DP 型（PREPARE/START/TRANSMIT/FINISH）か、MCU 型（BOOT へ落ちる）か

Air 系同士なら 1〜3 はほぼ共通です。**同じ XREAL でも系統が変われば通用しません** ——
One / One Pro / 1S は 16bit op の別プロトコルで、ここに書いたものとは別物です。
ベンダーが変わればさらに違い、たとえば Rokid は USB 制御転送と標準 DFU で、
何も共有していません。
