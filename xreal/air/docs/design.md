# XREAL Air（第1世代）— 何をどう変えているか

DP ブリッジに 39 レコード、MCU に 21 レコード。合わせて 1,700 バイトほどの変更です。
この文書はそれを機能単位で説明します。バイト単位の内容はビルダのレコード表そのものが
正本で、2つのイメージを diff すれば表と突き合わせられます。

前提知識はコンテナ形式（[../../../docs/container-format.md](../../../docs/container-format.md)）と
HID プロトコル（[../../../docs/hid-protocol.md](../../../docs/hid-protocol.md)）にあります。

---

## 何が問題か

パネルは 1920x1200 です。純正ファームウェアはそれを一度も広告しません。

| 入力 | 純正の扱い |
|---|---|
| `1280x720` | 対応するタイミングが EDID に無い |
| `1920x1080` | ネイティブとして広告。実際にはパネルの一部しか使わない |
| `1920x1200` | **存在しないことになっている** |
| Full-SBS 3D | `3840x1080` まで |
| USB データを持たない機器 | USB オーディオが使えず、手動で切り替えるしかない |

このビルドは4つの入力経路すべてと、音声経路を成立させます。

## DP ブリッジ側

### 論理モードと EDID の関係

グラスは論理モードを持ち、モードごとに違う EDID を出します。モード選択は HID の `0x08`、
現在値は `0x07` で読めます（[hid-protocol.md](../../../docs/hid-protocol.md) 参照）。

| モード | 用途 | このビルドでの広告内容 |
|---:|---|---|
| 1 | 自動・既定 | base に `1200p60/90/120`（先頭が preferred）、CTA に VIC 4 (`720p60`) と `1080p60/90/120` |
| 5 | 2D 72 Hz 固定 | base に `1200p72`（preferred）＋ `1080p72` |
| 10 | 2D 90 Hz 固定 | base に `1200p90`（preferred）＋ `1080p90` |
| 11 | 2D 120 Hz 固定 | base に `1200p120`（preferred）＋ `1080p120` |
| 3 / 4 / 9 | Full-SBS 3D | base に `3840x1200 @60 / 72 / 90`（HBR2） |
| 8 | Half-SBS | Air では未対応 |

**すべての 2D モードが `1920x1200` を preferred timing として広告します。** これが macOS で
効きます。macOS は base ブロック先頭の DTD からネイティブ解像度を決め、CTA の native フラグを
見ません。純正は base 先頭が `1080p60` なので、1200p は選択肢にすら出ません。

**専用モード（5/10/11、3/4/9）は CTA 拡張ブロックを持ちません。** 純正は全モードに
共通の CTA を付けるため、固定リフレッシュのはずのモードでもホストが無関係な
リフレッシュレートを選べてしまいます。拡張ブロック数を 0 にして、CTA は
モード 1 だけが持つようにしています。

Established Timings は空、Standard Timings は `01 01` × 8（未使用）です。
`720p60` はモード 1 の CTA だけに属します。

### 実行時 DTD ビルダと post-build helper

EDID の詳細タイミングは静的テンプレートから出るのではなく、モードごとの初期化子が
実行時に組み立てます。モード 1 の初期化子は DTD を 3 本、専用モードの共通ビルダは 2 本
書きます。

その後、**チェックサム計算の直前に post-build helper が走ります。** ここがこのビルドの
中心です。

```
E0BF == 2 (モード1)  → base スロット 0/1/2 へ 1200p60/90/120 をコピー
E0BF == 0 (専用モード) → BB からリフレッシュを判定し、
                        base スロット 0 へ同リフレッシュの 1200p を 1 本コピー
それ以外              → 何も書かない
```

専用モードでスロット 0 を 1200p が取ることで、ビルダが書いた同リフレッシュの `1080p` が
スロット 1 に残ります。**広告する集合は変わらず、preferred がどちらかだけが入れ替わります。**

この helper の挙動は、ビルダが 8051 エミュレータで `E0BF` の全 256 値 × `E0B9` × `E0BB` の
全ベクタを実行して検証します。どのモードがどのスロットに何を書くかが機械的に証明されます。

### CTA を 2 つ持ち、音声経路で選ぶ

モード 1 の CTA には 2 種類あり、`E0B8`（音声経路）で選ばれます。

| 経路 | CTA の内容 |
|---|---|
| USB オーディオ（`E0B8=0`） | VIC 4 ＋ `1200p60/90/120` ＋ `1080p60/90/120` |
| DP オーディオ（`E0B8=1`） | 純正の Audio DB / Speaker Allocation / HDMI VSDB を保持 ＋ VIC 4 ＋ `1080p60/90/120` |

**実効的に広告されるモード集合は両者で同一です。** base が `1200p` 三本を持つので、
USB 側の CTA にある `1200p` 三本は重複です。

その重複には理由があります。**モード 10/11 の post-build helper は、コピーする 1200p DTD を
USB 側 CTA のオフセット 24 と 42 から直接読みます。** つまりあの位置の 1200p 三本は
広告であると同時にデータソースでもあり、動かせません。1080p 三本はその後ろ
（オフセット 60/78/96）に足しています。

### 3D Full-SBS と HBR2

モード 3/4/9 は `3840x1200` を 60 / 72 / 90 Hz で出します。ピクセルクロックは
それぞれ `330.000` / `396.000` / `495.000 MHz` で、**495 MHz は HBR2 でしか成立しません。**
3D 経路だけをリンクレート HBR2 へ上げています。2D 側のリンクレート選択は変えていません。

### 入力の自動追従

実際に来ている信号の垂直アクティブ行数を分類し、`E086` に格納します。

| 入力 | `E086` |
|---|---:|
| 720 行 / 1080 行 | `0` |
| 1200 行 | `2` |

MCU がこれを読んでパネルを追従させます。**ホスト側で解像度やリフレッシュを切り替えても、
グラス側の操作は要りません。**

固定リフレッシュモードでは、分類したのと同じサイクルで内部のタイミング構造体も
同期させます。モード 5/10/11 × 1080/1200 クラスの組み合わせごとに、ピクセルクロックと
垂直タイミングが決まります。

| モード | 1080 クラス | 1200 クラス |
|---:|---|---|
| 5 | `1080/1125`, `178.200 MHz` | `1200/1250`, `198.000 MHz` |
| 10 | `1080/1125`, `222.750 MHz` | `1200/1250`, `247.500 MHz` |
| 11 | `1080/1125`, `297.000 MHz` | `1200/1250`, `330.000 MHz` |

水平方向はどれも active/total = `1920/2200`、sync/porch = `88/44/148` です。
垂直の front porch / sync / back porch は 1200 側が `9/5/36`、1080 側が `4/5/36`。

### 720p 入力

CTA に VIC 4 を広告することで、720p しか出せない機器がタイミングを見つけられるようになります。

線上に真の `1280x720`（`74.250 MHz` / total `1650x750`）が来たとき、**ブリッジはそれを
パネルへ拡大して全画面に表示します。** この拡大自体は純正のブリッジが持っている機能で、
このビルドが足したものではありません。品質は専用スケーラほどではないものの、実用に耐えます。

なお、このビルドはスケーラのワークスペース参照先を移動させています。純正のスケーラは
ゼロ初期化用に ROM の未使用領域を読みますが、その領域にこのビルドがコードを置いたため、
別のゼロ領域へ退避させる必要がありました。

## MCU 側

### パネルの追従

MCU は Sony のマイクロ OLED を 2 枚駆動します。DP ブリッジが 1200 行を出しているのに
パネルが 1080 行構成のままだと、正しく表示されません。

周期処理が `E086` を読み、パネルの行数設定を追従させます。

| 行数 | パネルレジスタ `0x3F` / `0x45` |
|---|---|
| 1200 | `00` / `D4` |
| 1080 | `01` / `5C` |

**パネルのタイミンググループもリフレッシュレートごとに違います。**

| リフレッシュ | グループ（`reg 0x61`） |
|---|---|
| 60 / 72 Hz | `0x11` |
| 90 Hz | `0x17` |
| 120 Hz | `0x1F` |

90 Hz で `0x11` のままだと縦筋が出ます。純正はモード 10 でも 3D の 90 Hz でもグループ 1 を
選ぶため、このビルドは 2D の各アームと 3D の 90 Hz を正しいグループへ向けます。

グループの適用にはキャッシュとの比較を挟み、既に目的のグループなら何もしません。
これがないと、パネル設定の途中状態（行数ペアが `00/5C` のような混在）が発生し、
画面の下端が切れます。

### 自動 DP オーディオ

**HDMI → USB-C 変換器やゲーム機は USB データを一切運びません。** USB オーディオが使えず、
かといって手動切替のボタンを押す人もいない状況になります。

純正でこの状態から音を出すには、利用者が長押しで切り替えるか、純正 Nreal Adapter が
専用のビットを立てるかのどちらかが必要です。

このビルドは USB の `SET_ADDRESS` を監視します。

```
ホストが一度でもアドレスを割り当てた
    → その給電セッションでは USB オーディオを維持（自動切替しない）

アドレスが 0 のまま約 5 秒経過
    → 純正の DP 音声遷移へ入る
      ・遅延させた 2 回目の B6
      ・保存済み音量の復元
      ・その給電セッション中は手動切替をロック

純正 Nreal Adapter の Attention 経路
    → 純正と同じく即時に遷移
```

PC 直結ではホストが必ずアドレスを割り当てるので、**誤って DP 音声へ落ちることはありません。**

**DP 音声モードに入ると USB 複合デバイスが閉じます。これは純正の挙動です。**
そのため DP 音声中は HID 制御が使えず、`xreal/` の診断ツールも動きません。

### cold 復帰

モード 10 には、電源投入や DP リセットの後で実際の `E0BF` を読み直し、正しい状態へ
再収束する経路があります。モード 5/11 には拡張していないので、cold の後にそれらを
使う場合は HID でモードを送り直す必要があります。

## 検証されていること

ビルダは結果を証明します。

- 純正の SHA-256 / projectCode / コンテナ CRC
- 各レコードの before バイト
- 決定論的な再ビルドと、出力の SHA / CRC / bank0 tag / 変更バイト数の pin
- 生成 EDID のデコードと契約照合（両 CTA の checksum、VIC 集合、DTD 集合、
  モード 10/11 が読むオフセット 24/42 が動いていないこと）
- post-build helper の全状態ベクタ実行

実機での測定結果は [verification.md](verification.md) にあります。
